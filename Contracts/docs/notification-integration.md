# Notification integration compatibility v1

- Public methods/paths remain the Notification OpenAPI v1 contract. Clients only call Gateway and ownership always comes from the Auth JWT subject.
- Consumers accept canonical `reputation.score.changed` (`payload.threatTargetId`) and legacy `reputation.updated` (`targetId`/`urlTargetId`). Score/level data uses the existing `newScore/newLevel` fields; Inbox deduplication is unchanged.
- Integrated Notification resolves each submitted watch URL through the private authorized Threat target API. Notification persists a schema-local binding to the returned UUID; neither a public targetId parameter nor cross-schema access is introduced. The watched URL is never fetched. Public watch IDs/canonicalization remain compatible; multiple Threat IDs may bind to one existing watch without rewriting Threat data. Both the submitted URL and Notification's displayed sorted-query URL are bound, because Threat intentionally preserves query order.
- Additive Notification V3 creates `notification.watchlist_targets` and preserves existing watches. Re-adding an existing watch is idempotent and binds it without a second WATCHLIST_ADDED notification. Existing standalone deployments may omit both private Threat settings and retain legacy event matching; integrated release configuration requires both. Existing watches should be re-added through their owner's authenticated API to populate bindings before canonical-only event delivery is accepted.
- Report lifecycle notifications keep the existing canonical reporterUserId/reportId/status payload. Search/Campaign/Analytics and FCM physical-device delivery retain their separate acceptance criteria.
